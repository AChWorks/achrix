# AChrix — Master Specification

Canonical project intent for `AChWorks/achrix`. Detailed rules have one owner each, located through the [Project Map](PROJECT-MAP.md).

## Mission

AChrix is a reusable, versioned AChWorks Foundation for web-connected applications. Its purpose is to shorten the path from an idea to a maintainable product by sharing useful engineering capabilities while each product keeps its differentiating business behavior.

**AChrix is a coherent, long-lived product-building Foundation, not merely a collection of libraries or a one-time starter.** Suitable products should be able to start on its maintained Core and selected Modules, remain independently owned while consuming their later compatible releases, and grow through supported extension/composition contracts rather than edits to AChrix source. The normal path from initial composition to an independently maintained product must be understandable: predictable conventions, documented extension and operations, safe authorization, explicit compatible version sets, and upgrade/recovery evidence. This is AChrix's own product and technology identity, not a claim to be a general-purpose framework.

`AChrix` is the project/technology name; Foundation is its architectural category. Pronunciation: `ATCH-riks` (Persian: `اَچ‌ریکس`). Suitable consumers include content sites, SaaS, marketplaces, commerce, financial products, media, APIs and automation; none must adopt unrelated modules or infrastructure.

Koinon owns AChWorks cross-project governance/discovery/contracts. AChrix owns its implementation, application-specific contracts, Core/Modules, packaging and releases. Koinon is not a runtime dependency or a prerequisite for public consumers to understand the usage and extension rules published here. Ecosystem-wide coordination policy and AChrix-specific engineering/module design are distinct ownership layers: AChrix can use Foundation-family-specific reuse, dependency and interoperability rules within compatible ecosystem boundaries, without imposing its technology choices on unrelated projects.

## Durable boundaries

1. **Minimal Core.** Core contains only broadly required composition, capability identity, application/authorization and lifecycle contracts. Useful product features do not automatically belong in Core.
2. **Owned Modules and products.** A Module owns one coherent reusable behavior domain, any durable state/assets that belong to it, and may expose a bounded set of related Capabilities. Cross-module mutations use its authorized Application boundary. Reusable Modules may own generic mechanics used inside independently owned products; products still own their domain/business semantics, product account/profile meaning, permission grants, data, releases and deployment. Optional SSO does not create shared central account ownership.
3. **Ongoing versioned consumption and upgrades.** Products build **on** the official Core and selected independently versioned Modules using reviewed public contracts and pinned compatible dependency sets, not copied sources, product-specific Foundation patches or private implementation imports. AChrix maintains and releases shared behavior once; each product deliberately adopts a compatible combination, verifies its own integration and data/migration requirements, and rebuilds/activates a coherent product artifact when required. Compatible releases should remain consumable without rewriting independently owned product behavior; breaking API/schema transitions may require explicit adaptation and recovery. Independent component versioning does not promise live hot-swapping, automatic production updates or independent replacement of code already linked into one binary; it does not require separate services, processes or databases.
4. **One Application surface.** Human UI, HTTP/API, MCP/AI, CLI and jobs use the same behavior and authorization. Relevant internal and external programmatic use is part of capability design and completion: deliver applicable HTTP API and MCP access alongside the capability, with explicit justified exceptions or tracked remaining scope. In-process callers may use the owning service directly. Machine access never grants extra authority. [Contracts](architecture/contracts-and-interfaces.md#internal-and-external-programmatic-coverage) owns coverage and compatibility rules; a Go export is not proof of network support.
5. **Extension without Foundation modification.** Publish small supported versioned extension/Application/Module contracts; keep implementation private. Products implement their domain behavior and extend AChrix through these public seams. When a needed generic capability or extension seam is missing, evolve it upstream in AChrix with compatibility and consumer proof rather than patching or shadow-forking its internals per product. Stable capability/protocol identity is separate from branding. External libraries, modules and services may be used directly or through the smallest valuable adapter without becoming AChrix-owned.
6. **Safe state and effects.** Data invariants, security, compatibility, migrations, external side effects and recovery are owned and testable. Unknown mutation outcomes are reconciled rather than blindly retried. A source upgrade is not proof of a safe deployed/data upgrade.
7. **Reuse-first placement, evidence-based implementation/extraction.** When current product knowledge makes a coherent capability more likely than not to recur across product classes, establish the reusable Module ownership boundary before the first product duplicates it. Implement only real near-term behavior, and keep uncertain/product-specific semantics local. Independent packages, repositories, services or databases still require their own evidence and cost justification.
8. **Public meaning for humans and machines.** Products exposing public web content preserve semantic, accessible and truthful output for people, search and AI retrieval. [Web](web/seo-and-semantic-web.md#public-content-and-ai-retrieval) owns the detailed publication rules; Core gains no mandatory SEO, content or crawler subsystem.

The default is a modular monolith. Inspect maintained standards/native/ecosystem capabilities, but select internal ownership versus an external dependency by the **long-term** security, control, interoperability, portability, licence, maintenance, upgrade and replacement trade-off, never implementation speed alone. AChrix deliberately owns reusable product-building capability semantics where shared ownership lowers lifetime cost and protects evolution; low-level established implementations may still be appropriate under reviewed dependencies. Avoid exposing provider/library details as enduring public contracts or forcing an external runtime/service. [Engineering principles](principles/engineering-principles.md) own the evidence rules; the [Module model](architecture/module-model.md) owns detailed placement and accepted reusable Module boundaries.

## Starting path

- Go is the primary shared implementation language: [ADR-0002](decisions/ADR-0002-go-primary-implementation.md).
- Ordinary PostgreSQL is the first relational and integration-test target: [ADR-0003](decisions/ADR-0003-postgresql-and-optional-infrastructure.md) records the rationale and optional-infrastructure boundary. [Operations](operations/operability-performance.md#supported-environment) owns tested versions; the component manifests own actual dependencies.
- Use independently versioned Core and official Module dependencies with an independent pinned consumer: [ADR-0006](decisions/ADR-0006-independent-components-and-lifecycle.md). [ADR-0005](decisions/ADR-0005-initial-go-consumption.md) records the original single-module starting point.
- Exact supported versions, public APIs and installation/upgrade behavior require executable proof. A named technology or interface is not tested support.

Go is the current primary implementation path, not a universal-language mandate. A product may use another justified runtime/provider/database through an explicit, intentionally versioned boundary; concrete cross-runtime support must be proven for that interface and consumer, not assumed for all in-process Modules. The architecture should keep such future interoperability viable when cheap and credible, without building unneeded adapters. This does not force migration of other repositories or require a central AChrix service.

## Non-goals

- A copy-and-modify starter as the architecture, an all-purpose framework identity, or mandatory microservices. A coherent, supported product starting experience is a goal; it must compose maintained Modules and versioned contracts rather than duplicate their sources.
- Universal entity/field/value storage, wrappers around every library, or one package/service per Module.
- Every database, provider, delivery adapter, tenant/feature-flag engine or future product feature built in advance.
- Mandatory cache, broker, workflow engine, search cluster, company account, container runtime or orchestrator.
- A marketplace, registry, certification/cloud platform or dynamic plugin runtime before a concrete need.
- Thirty-year compatibility guarantees, zero-cost migrations, or claims of measured performance/security before evidence exists.

## Quality contracts

The following are product-relevant obligations, not a demand to implement every subsystem immediately:

Preserve explicit ownership/consistency, stable public identity, correct time/money semantics and privacy; default-deny authorization and secret-safe AI/public access; actionable contracts and recoverable effects; compatible stateful upgrades and verifiable releases; bounded resources and useful diagnosis; semantic accessible web, Unicode/RTL and content independent from presentation. The [Project Map](PROJECT-MAP.md) locates each detailed rule owner.

## Licensing and ecosystem

Core remains clean, maintainable and genuinely open source. [Licensing](legal/licensing.md) owns code/artifact terms; [Governance](../GOVERNANCE.md), [Contribution Agreement](legal/cla.md) and [Trademark Policy](../TRADEMARKS.md) own stewardship, incoming rights and representation.

The aim is **easy to extend, but expensive to impersonate** through trustworthy compatibility, official Modules, security maintenance, tooling, documentation and release identity. Do not achieve it through obfuscation, confusing code, Core license checks, mandatory online services, artificial incompatibility or restrictions contradicting open-source rights. Lawful forks remain possible. Future registry/signing/certification/update services must justify their own implementation cost.

## Proof and success

The first executable outcome proves minimal Core, a necessary extension, real PostgreSQL behavior and one shared Application/authorization path from an independent consumer and a necessary delivery adapter. Do not build all adapters or optional Modules to prove the concept. The first real product/consumer is chosen from actual product need and may be content/CMS, SaaS, marketplace/commerce, API/automation or another suitable application; no product class is an AChrix prerequisite. It should consume only the accepted reusable Modules it actually needs instead of reimplementing their shared mechanics, while its product/domain semantics remain independently owned. A later materially different consumer validates/refines those shared boundaries and reveals additional reuse; it is not a mandatory prerequisite for every clearly reusable Module decision. [Roadmap](development/roadmap.md) owns this sequence; GitHub Issues own scope and execution gates.

Success means suitable products can **stay on AChrix across subsequent supported Core/Module releases** while retaining independently owned product code and domain state; shared fixes and capabilities are maintained once and reach each product through deliberate, validated dependency updates instead of repeated forks or manual source synchronization. Optional infrastructure remains optional, product semantics remain independently owned, and compatibility/security/data/recovery boundaries are verifiable. This shared path is the preferred default for AChWorks products where AChrix fits because it lowers aggregate delivery, upgrade and maintenance cost as the product portfolio grows; it is not mandatory for an unsuitable project. A product may intentionally stop consuming AChrix, but doing so transfers replacement, data migration, security and future maintenance responsibility to that product; no transparent exit or continued shared updates are promised. Humans and AI must recover intended behavior and current work without chat history.

For products with an administration UI, routine compatible Core/Module installation and upgrades should be simple product actions without user-run server commands. AChrix owns reusable installation/update mechanics and their contracts; products own their requirements, prepared composition and safe activation/recovery. Supported environment adapters must be verifiable and extensible beyond one product, control panel or processor architecture. Core remains the application foundation rather than a host administrator.

## Documentation authority

This specification owns mission, non-goals, durable boundaries and success criteria. Topic documents own current operational and technical rules; a compact ADR records a consequential accepted choice when its rationale or trade-offs will guide future work. Retain a superseded ADR only when its rationale still informs a consequential future decision, supported consumer or migration; other replaced choices remain recoverable in Git/PR/Issue history. Git/PR/CI/releases own delivery facts, Issues own live work, README is the entry point and the Project Map is the index.

Before adding or retaining a document, identify the real reader, decision or action it supports, and why an existing contract, source, test, Issue or Git history does not already answer it. Keep one canonical rule owner, link instead of copying, and reconcile affected references when that rule changes. Do not turn provider possibilities, superseded options or mutable task status into permanent technical requirements. Resolve material contradictions before affected work; repository text and chat history never grant mutation authority.
