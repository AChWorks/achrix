# ADR-0007 — Optional OAuth authorization: interoperable profile and security gate

Status: **proposed for independent review**. No permanently selected protocol engine, approved public authorization contract, official release or production activation exists. The non-production, independently unreviewed candidate is documented in [OAuth](../../oauth/README.md); it is not adopted by this ADR.
Date: 2026-11-04.
Outcome: [OAuth/OIDC #125](https://github.com/AChWorks/achrix/issues/125), prerequisite of [Bridge #5](https://github.com/AChWorks/achrix/issues/5).

## Current ownership and evidence

[Identity](../../identity/README.md) owns product-local account and session authentication. The optional [Bridge](../../bridge/README.md) owns HTTP/MCP **resource-server** admission: its existing RFC 9728 protected-resource metadata locates configured authorization issuers, while a product-provided token verifier and current application policy decide actual access. Bridge does not run an authorization server, consent flow or refresh-token store. A token must not substitute for the product's current rights.

AChrix is accepted as owner of **reusable optional authorization mechanics**, not product users, product permissions, a central AChWorks account service, or hosted client/onboarding UX. Future AChrix authorization needs its own optional versioned component boundary, using existing Identity and Bridge public contracts without importing their infrastructure or putting OAuth in Core. Products still own sessions, UI, roles, site/resource relationships, runtime/release and credential custody.

## Proposed smallest interoperable profile

For the **first executable issuer slice**, select OAuth **authorization-code with mandatory PKCE S256**, for explicitly enrolled public or confidential clients; implicit and resource-owner-password grants are out. Require canonical HTTPS issuer and one configured resource/audience. Publish RFC 8414 Authorization Server Metadata and RFC 9207 issuer identification in authorization responses, including errors. Bind the code and token exchange to the same exact client, redirect URI, user, issuer and resource. Require the RFC 8707 resource parameter at both authorization and token endpoints; reject token passthrough to another API. Advertise only endpoints and methods that actually work.

**Start with pre-enrolled clients**, each with exact redirect URIs, bounded scopes and a registered token-endpoint authentication method. Distinguish **client identification**, **client authentication** and **user-delegated authorization**:
- A registered **public client** has an identifier (`client_id`) but cannot authenticate itself merely by presenting that identifier. Its `token_endpoint_auth_method` is `none`; PKCE S256, registered redirect matching and active user consent defend the delegated flow, **not** the authenticity of the public application. Never treat a public `client_id` or a previously remembered approval as a trusted-client privilege or a substitute for fresh user/session/consent validation. A copied public `client_id` alone must never grant another user's code, token, consent transaction or permissions. This does **not** claim the server can cryptographically distinguish two otherwise identical public-client installations.
- A registered **confidential client** must authenticate with its pre-registered supported method and protected credential at the token endpoint, including **refresh**; mismatched, absent, downgraded or substituted authentication methods fail closed. Confidential authentication establishes the registered client, **not** permission to act for a user. Mandatory PKCE S256 still applies.
- Consent decisions must refer to the actual authorized user, the registered client configuration, its exact redirect and requested resource/scope. Do not infer that public-client identity is cryptographically proven. Test copied public `client_id`, substitution of redirect/client across requests, wrong confidential secret, missing authentication, method downgrade and consent reuse under another user/client.

This pre-enrollment path is described by [ChatGPT MCP plugin authentication](https://developers.openai.com/plugins/build/auth) and [Claude custom connector setup](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp); actual client interoperability is **not proved** by those documents. User-supplied client identifiers must not cause arbitrary outbound metadata fetches in the initial profile.

**CIMD, not DCR, is the intended future direction:** [MCP specification 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/) prioritizes Client ID Metadata Documents and deprecates DCR for future profiles. The currently evolving [CIMD draft-ietf-oauth-client-id-metadata-document-03](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-03) is **not an RFC**. Before admitting URL-based clients, separately define SSRF and DNS-rebinding resistance, redirect/domain constraints, issuer-scoped stable identity, bounded fetch size/deadlines/redirect rules, cache revalidation and metadata changes. Implement DCR only for an evidenced legacy client requirement with limits, retention and authorization—not for compatibility speculation.

OAuth does not automatically imply **OIDC identity-provider** support. Do not advertise OIDC Discovery, ID tokens, userinfo or JWKS until a real consumer requires them and signed claims, key storage and rotation are proved. These are still in Issue #125's full outcome, not silently dropped.

### Minimum issuer discovery and response metadata contract

The first issuer must publish its own **RFC 8414 OAuth Authorization Server Metadata**, independently from Bridge's existing **RFC 9728 Protected Resource Metadata**. HTTP contract tests must retrieve both documents and validate the exact canonical values below, not merely confirm that a handler returns JSON.

| Required issuer metadata property | First-profile assertion |
| --- | --- |
| `issuer` | Exact configured HTTPS issuer; identical to the configured authorization server URL in the resource's `authorization_servers` and to the `iss` parameter on each authorization response, including error responses as applicable. Do not derive from request `Host` or forwarded headers. |
| `authorization_endpoint` | Canonical HTTPS URL of the **working** authorization-code endpoint for this issuer. |
| `token_endpoint` | Canonical HTTPS URL of the **working** code-exchange/refresh endpoint for this issuer. |
| `response_types_supported` | **Required by RFC 8414**: explicitly publish `["code"]` for the first profile. Reject `token`, hybrid/implicit or any other unimplemented response type; this field must not be omitted. |
| `grant_types_supported` | Explicitly publish `["authorization_code"]`, adding `"refresh_token"` **only if** refresh exchange is implemented and tested. Never omit this field: RFC 8414 otherwise defaults to `["authorization_code", "implicit"]`, falsely advertising an excluded grant. |
| `response_modes_supported` | Explicitly publish `["query"]` for the first code-only redirect profile. Add another mode (such as `"form_post"`) only after implementation and HTTP contract proof. Do not omit: RFC 8414 otherwise defaults to `["query", "fragment"]`; never advertise or accept unsupported `fragment`. |
| `code_challenge_methods_supported` | Must include `S256` (the first profile **requires** S256); do not silently allow `plain` or omitted PKCE. |
| `authorization_response_iss_parameter_supported` | Explicit Boolean `true`, with a correctly populated `iss` in real authorization success/error redirects per RFC 9207. |
| `token_endpoint_auth_methods_supported` | Explicitly list only implemented methods for enrolled clients: `none` for a supported public-client path and each **actually implemented** confidential authentication method (for example, `client_secret_basic` only if implemented). Do not omit: RFC 8414 otherwise defaults to `client_secret_basic`. Wrong or downgraded methods must fail. |

Future HTTP contract tests must GET the issuer-derived `/.well-known/oauth-authorization-server` discovery path per RFC 8414 (including issuer path components when present), require a successful JSON document, and assert the **effective** capability set after applying any RFC 8414 omission defaults. `response_types_supported`, `grant_types_supported`, `response_modes_supported` and `token_endpoint_auth_methods_supported` are **explicitly required by this first profile** even where RFC 8414 defines omission defaults: never accidentally imply `implicit`, `fragment` or `client_secret_basic`. Verify the advertised response type (`code`), grant (`authorization_code` plus implemented `refresh_token` only), modes (`query` only initially), PKCE (`S256`) and exact supported token-authentication methods against real working endpoints and **negative HTTP tests** for unsupported values. If a future revocation endpoint is advertised, evaluate its separate RFC 8414 `revocation_endpoint_auth_methods_supported` default (`client_secret_basic`) and advertise the actual implemented methods; any JWT client-auth method requires its applicable signing-algorithm metadata. Do not advertise optional endpoints, OIDC, implicit/password, or extensions that have not been implemented and verified. Cross-check issuer equality **across issuer metadata, authorization redirects and Bridge resource metadata**. Missing required fields, misleading omitted-field defaults, wrong issuer/resource, inconsistent redirect `iss` or unsupported advertised methods are acceptance failures. These are obligations for the **future issuer**, not claims that the current Bridge already emits them.

## Security invariants and required tests

| Boundary | Requirement and discriminating failure |
| --- | --- |
| User and consent | The real authenticated product user session identifies the authorizing user. Consent explicitly binds this user, the **registered client configuration** (not proof of public-client authenticity), audience, product/site and scope. Matching email, claimed actor, copied public `client_id` or Gateway session cannot establish an account link. Two users cannot exchange grants. Require active user authorization; never let confidential-client authentication alone grant delegated rights. |
| Client-supplied state versus AS CSRF | The OAuth **client's** optional `state` is an opaque value to **echo unchanged** in the authorization response and to validate at that client; it is **not** authorization-server login/consent CSRF protection. The AS must maintain its **own unguessable, one-use, expiry-bounded login/consent transaction** bound server-side to the current authenticated product user session, client, issuer, redirect, resource and requested scopes. Protect all AS login/consent submissions from CSRF (session-bound anti-CSRF verification plus Origin/Referer controls where appropriate); reject missing/stale/reused transactions, user switching, consent from a different session and unauthenticated approval, including when client `state` is present or replayed. |
| Redirect and issuer | Registered redirect URIs compare **exactly**; reject wildcard, userinfo, fragments, unregistered callbacks, open-redirect or query confusion. Bind every AS transaction to the exact issuer and user session; reject mix-up using RFC 9207 `iss` in success and applicable error responses. Echo the client's `state` without promoting it into AS authority. |
| Authorization code | Code is short-lived, unpredictable, hashed at rest and redeemed **once atomically**, with its recorded client, redirect, issuer, resource, consented user, grant and S256 challenge. Reject public-client impersonation with another redirect, missing/wrong PKCE verifier, client-authentication method downgrade, simultaneous redemption, reused code and replay. |
| Audience and scope | Client resource parameter must be exact in both phases; returned token is bound to its sole intended resource. A valid connection scope only narrows product Application authority; wrong audience, site, client or product account is denied. |
| Token profile | Prefer opaque high-entropy short-lived access tokens with durable verifier material and no public JWT dependency initially; validate issuer/resource/client/expiry/current grant and account status on **every request**. No token content/secret in logs or stored plaintext. |
| Refresh | Every refresh token is bound to its **original authenticated user, registered client, durable consent grant, issuer, exact resource and originally approved scope ceiling**. Re-evaluate current user/grant/client validity; confidential clients must authenticate using their registered method at refresh, whereas a public `client_id` remains identification only. Reject cross-client, cross-user, cross-resource, method downgrade, grant substitution and **scope widening** even when a rotated token is valid. Specify lifetime, **atomic rotation**, single-use/replay detection, family invalidation, simultaneous refresh behavior, revocation, retained-state recovery and cleanup; test independent client/resource families under concurrent refresh and revocation. |
| Revocation and logout | User/admin grant revocation or disconnect invalidates subsequent use of the grant and its access/refresh family; user disablement/client disablement must also prevent later protected operations. Product **interactive-session logout** clears the local browser session and invalidates pending AS login/consent transactions but **does not implicitly revoke already consented OAuth grants** by default. Any distinct **AS ceremony logout** clears only the AS ceremony session/pending transactions and does not silently log out unrelated product sessions or revoke grants. **Explicit grant revocation** is a separate user/admin action; if a product requires logout-to-revoke, declare and obtain Owner approval for that stricter product policy before implementation. The Owner has accepted the non-revoking normal logout rule; do not reopen that decision without new material evidence. Where AS and product share the same login session, one logout invalidates that session and the pending AS transactions tied to it. No OIDC front-/back-channel logout support is advertised. Prove logout isolation, pending-transaction invalidation, explicitly revoked grants, cross-client/resource effects and failure of a revocation dependency. Completed business effects remain completed. |
| State | Normal PostgreSQL transactions must own code, grant, refresh and revocation consistency. Specify versioned migrations and restore of retained revocations; code rollback is not data rollback. Do not share Identity's internal tables across component boundaries. |
| Security keys | Secrets are provided by product-controlled secure runtime sources. If asymmetric JWT/ID token support is later selected, first prove key rotation with JWKS/kid overlap and revocation; no hand-written cryptographic primitives. |
| Bounded execution | Limit metadata, request/response bytes, client count, active work, state TTL, consent attempts, token refresh and expensive crypto. Constructed-but-idle capability starts no network poller or per-client worker. |
| Diagnostic boundary | Public denials identify a safe error, correlation and corrective action; protected logs preserve phase and provider/DB cause with targeted redaction. Tokens, codes, verifier, private fields and signing keys never enter public diagnostics. |
| Availability | Issuer/DB/key/consent service unavailable means unavailable; not anonymous access, fallback issuer, implicit approval or a successful empty grant. |

Canonical references: [OAuth 2.0 Security BCP RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html), [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html), [RFC 9207](https://www.rfc-editor.org/rfc/rfc9207.html), [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728.html), [RFC 8414](https://www.rfc-editor.org/rfc/rfc8414.html), [Browser-based Apps RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html). Standards describe required behaviors, not evidence that any chosen SDK implements them.

## Engine/dependency decision — selected for a bounded optional implementation

| Candidate | Benefit | Cost / proof gap | Recommendation |
| --- | --- | --- | --- |
| Small in-house protocol server with maintained crypto/JOSE primitives | Tight control, small runtime graph | We would own authorization-code, PKCE, refresh, issuer, redirect and registration security indefinitely, including future RFC changes | **Do not write a new security protocol engine merely for speed** |
| [ZITADEL OIDC Go v3](https://github.com/zitadel/oidc) | Apache-2.0, maintained in 2026, in-process provider and explicit storage interfaces; can support OIDC if later needed | Nontrivial dependency graph, concrete PostgreSQL adapter and product session adapter still needed; check resource binding, CIMD and CORS against actual version | **Owner-selected implementation candidate**; pinned optional module dependency; security acceptance pending |
| [ORY Fosite](https://github.com/ory/fosite) | Apache-2.0, extensive OAuth/OIDC framework and storage extension | Larger transitive graph and older latest published version; no demonstrated 2026 CIMD/profile fit | Fallback to compare if first candidate fails |
| [ORY Hydra](https://github.com/ory/hydra) or hosted IdP | Maintained separate authorization-service pattern | Separate runtime and provisioning, key custody, deployment/vendor lifecycle, and product consent integration | Optional real-product deployment choice, **not** mandatory Foundation infrastructure |
| Small generic OAuth servers | Potentially fewer packages | No justified OIDC/registration/security completeness from the available evidence | Not selected |

An isolated **API-only Go 1.27.3 spike** resolved ZITADEL OIDC v3.51.17 using ordinary Go modules (41 modules including the spike after tidy) and successfully compiled a test against its OpenIDProvider HTTP handler and authorization storage methods for code issue/exchange, access/refresh tokens, revocation and session termination. This proves that a suitable API seam exists, **not** that its behavior, security, resource semantics, CORS defaults, persistence or client interoperability are acceptable. The historical disposable spike did not add a dependency; the Owner-approved implementation now pins v3.51.17 **in the optional oauth module only**.

A library is an **engine**, not a product-independent persisted schema or permission source. Keep AChrix grant semantics and identities independent from its internal storage, subject to real integration evidence. Do not import any candidate into Core, Bridge or the existing Notes consumer simply to reserve a framework. Defaults from sample login/storage/CORS implementations are not production decisions.

### Owner-approved choice and exit strategy (2026-11-05)

Option B and the **concrete maintained library** `github.com/zitadel/oidc/v3 v3.51.17` are approved for a **private, optional Go OAuth adapter** (see [Issue #125 decision](https://github.com/AChWorks/achrix/issues/125#issuecomment-6649025517)). Preserve neither the old bespoke engine nor the test candidate's API merely for sunk-cost reasons. Prefer tested high-value policy/session/storage logic, and aggressively remove duplicated or obsolete protocol paths.

The first runtime deliberately **does not use the full ZITADEL OIDC Provider**: its `CreateTokenResponse` also creates an ID Token, while the supported AChrix profile is OAuth-only. The private adapter instead uses upstream code/client/PKCE/refresh validation functions and the AChrix-owned PostgreSQL token/grant/consent lifecycle. The SDK's native plain-PKCE acceptance and scope-filtering behavior are explicitly narrowed by AChrix ingress guards; SDK native `AuthRequest` carries no required RFC 8707 resource, so AChrix binds a single exact resource in its durable grant and both HTTP phases. RFC 8414/9207 metadata and redirect semantics are likewise AChrix-owned.

Provider-specific types/config/storage must remain package-private; Core and Bridge must not import the engine. The initial pre-enrolled client configuration bounds the **mandatory current product ClientLookup** and cannot silently expand. A future engine switch retains product-facing Grant/VerifyAccess/Disconnect/Consent contracts but may require an explicitly reviewed data migration, token expiry or fresh consent; there is **no** promise of zero-downtime token portability or simultaneous engines per issuer.

Why not other candidates: Fosite v0.49.0 has materially larger tested dependency graph, longer release gap and a public unconfirmed memory-exhaustion report; it also requires an exact RFC 8707 resource/issuer adapter. go-oauth2 v4.6.0 would leave more of AChrix's standards profile unimplemented. A permanently bespoke engine carries long-term protocol-security maintenance. Hydra is an optional externally hosted service comparator, not this in-process Foundation component. Real resource/callback/refresh/metadata, API/SQL and live client interoperability tests remain hard acceptance gates.

## Next executable implementation gate

1. Using the Owner-selected v3.51.17, prove the bounded adapter implements exact code+S256/resource/issuer profile and integrates with existing product Identity and Bridge callbacks. Inspect the pinned module graph, supply-chain exposure, licensing and replacement cost; do **not** treat dependency selection as complete security acceptance.
2. Implement a dedicated optional authorization component and bounded PostgreSQL storage/secret adapter. Verify atomic code exchange; public-client `client_id` impersonation; confidential-client authentication/method downgrade; client-`state` echo versus **independent AS session-bound CSRF**; user/session switching, stale/replayed consent; refresh rotation/replay and binding to original user/client/grant/scope/resource; product versus AS logout versus explicit grant revocation; multi-user/client/resource/site isolation; actual RFC 8414/RFC 9207 metadata and redirect `iss` assertions; and account/permission freshness. Do not implement new product business roles.
3. Prove ordinary UI and MCP/HTTP invoke one owning Application operation with two users and current rights. Where actual clients require it, add CIMD/OIDC/DCR via separately reviewed profiles; do not advertise unimplemented capability or claim real-client support based only on a fixture.
4. Perform supported versioned consumer, migration/restore, resource/latency, local HTTPS/browser and genuine client onboarding acceptance. Require fresh author-separated **HIGH_ASSURANCE** security/correctness review plus Owner authorization for public security/compatibility commitments and any production rollout.

## This package's precise delivery boundary

The accompanying Bridge test proves only that the **existing** protected-resource metadata and anonymous Bearer challenge contain the trusted resource and issuer, even when an HTTP request supplies hostile Host/forwarded headers. It does **not** test OAuth authorization, PKCE, consent, tokens, refresh, a product editor, a real client, or deployment.

This is the first **protocol/dependency decision gate** under Issue #125. The Issue remains open: no issuer, new Module, migrations, new vendor dependency, release or cross-repository mutation is delivered here. The profile remains a proposed security contract until independently reviewed and the consequential decisions are accepted.
