# Development Roadmap

This is the outcome sequence. GitHub Issues own current scope, decisions, execution gates and progress; documentation publication alone does not authorize implementation.

1. **Executable Foundation:** minimal Core, a necessary extension, real PostgreSQL and an isolated pinned consumer. Prove one Application capability/authorization path with a necessary HTTP/API adapter, then meaningful tests/CI and supported version evidence. [Issue #1](https://github.com/AChWorks/achrix/issues/1) owns acceptance; [ADR-0005](../decisions/ADR-0005-initial-go-consumption.md) owns the starting consumption shape.
2. **Initial reusable Modules + first real CMS:** use the reuse-first placement rule before the product recreates clearly shared mechanics. Identity, Admin and Media are the initial accepted reusable Module ownership boundaries under the [Module model](../architecture/module-model.md). Implement only the bounded real slices the first CMS needs, in the existing AChrix repository/Go module by default; do not create empty framework surface or independent repositories/services merely because placement is shared. The CMS remains a separate product/consumer and keeps its content/product semantics independently owned.
3. **Stateful lifecycle:** prove simple in-product Core/Module installation/update, compatible prepared composition, migration/activation, scoped backup/restore and safe cross-component diagnosis on that product. Routine users should need no server commands; do not extract an updater until repeated mechanics justify it. [Issue #19](https://github.com/AChWorks/achrix/issues/19) tracks AChrix lifecycle/backup compatibility evidence and product handoff.
4. **Different real consumer:** compare the accepted shared Modules against a materially different product, refine boundaries where evidence differs and identify additional reusable capabilities without assuming every repeated feature belongs in AChrix.
5. **Additional shared assets and earned extraction:** apply the reuse-first rule to new capabilities when current evidence already makes cross-product ownership more likely than product-local ownership. Use later consumers to validate/refine those decisions. Extract independent Go modules, repositories, services or additional database/provider support only when their separate release/ownership/operations economics are actually justified.

Registry/marketplace infrastructure, every delivery adapter and speculative optional Modules are not prerequisites. Stop planning when the next bounded task is discoverable and verifiable; implement and measure to resolve remaining uncertainty.
