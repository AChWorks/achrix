# Development Roadmap

This document owns the durable outcome sequence. GitHub Issues, PRs, CI and Releases own current scope, execution gates, dependency identities, progress and delivery evidence.

1. **Executable Foundation** ([Issue #1](https://github.com/AChWorks/achrix/issues/1)): establish minimal Core composition/authorization/lifecycle, a necessary extension, real PostgreSQL behavior and an isolated normally pinned consumer. Prove one shared Application policy path through at least one real delivery adapter, then meaningful validation and supported-environment evidence. [ADR-0005](../decisions/ADR-0005-initial-go-consumption.md) owns the starting consumption shape.

2. **Core hardening before reuse multiplies assumptions** ([Issue #44](https://github.com/AChWorks/achrix/issues/44)): keep optional-capability composition, authorization/lifecycle admission, public error semantics, diagnostics and Go quality/performance evidence bounded and explicit. Breaking public behavior follows the lifecycle/versioning policy rather than silently changing a published compatible line.

3. **Reusable Modules plus real consumers:** use the [Module model](../architecture/module-model.md) and reuse-first placement rule before a product recreates clearly shared mechanics. Stable implementation/evidence references include [Multi-Site #4](https://github.com/AChWorks/achrix/issues/4), [Search #48](https://github.com/AChWorks/achrix/issues/48) and [Settings #50](https://github.com/AChWorks/achrix/issues/50); their live task state remains GitHub-owned. Identity, Admin, Media, Audit, Notifications, Search, Settings, Backup & Recovery and optional Multi-Site are reusable ownership boundaries, but implementation remains demand/evidence driven. The [Multi-Site package](../../multisite/README.md) owns bounded exact-authority resolution; product isolation, data/storage ownership and retained-state update proof remain product concerns. Search requires a real search flow, Settings requires concrete reusable application-level fields, and Notifications requires a real delivery flow. Keep reusable Modules in the existing AChrix repository/Go module by default and do not create empty framework surface or independent repositories/services merely because placement is shared.

   [Rixa](https://github.com/AChWorks/rixa) is an early real consumer for selective composition, site isolation, Media/publication boundaries and aggregate operational evidence. Exact Foundation readiness, selected release identity and Rixa execution state stay in machine dependency state and GitHub work items, not this roadmap.

4. **Stateful lifecycle and reusable recovery evidence** ([lifecycle proof #19](https://github.com/AChWorks/achrix/issues/19), [Backup & Recovery #49](https://github.com/AChWorks/achrix/issues/49)): prove simple product-facing Core/Module installation/update, compatible prepared composition, migration/activation, scoped backup/restore and safe cross-component diagnosis on a real product/deployment profile. Routine users should not need ad-hoc server commands. Extract reusable updater/recovery mechanics only after product evidence establishes the boundary; do not infer a host daemon or generic backup engine from architectural placement.

5. **Materially different real consumer:** compare accepted shared Modules against another product class, refine Module/Capability granularity where evidence differs and identify additional reusable capabilities without assuming every repeated feature belongs in AChrix.

6. **Earned extraction and ecosystem assets:** extract independent Go modules, repositories, services, registries/signing/update tooling or additional provider/database support only when separate release cadence, ownership/security, deployment/runtime isolation or lifetime economics justify the added system cost.

Registry/marketplace infrastructure, every delivery adapter and speculative optional Modules are not prerequisites. Stop planning when the next bounded task is discoverable and verifiable; implement and measure to resolve remaining uncertainty.
