# Development Roadmap

This is the outcome sequence. GitHub Issues own current scope, decisions, execution gates and progress; documentation publication alone does not authorize implementation.

1. **Executable Foundation:** minimal Core, a necessary extension, real PostgreSQL and an isolated pinned consumer. Prove one Application capability/authorization path with a necessary HTTP/API adapter, then meaningful tests/CI and supported version evidence. [Issue #1](https://github.com/AChWorks/achrix/issues/1) owns acceptance; [ADR-0005](../decisions/ADR-0005-initial-go-consumption.md) owns the starting consumption shape.
2. **Pre-module Core hardening:** resolve the concrete v0.1 contract gaps discovered before shared Modules multiply them: executable optional-capability composition plus bounded/distinguishable authorization/lifecycle admission semantics under [Issue #44](https://github.com/AChWorks/achrix/issues/44). Coordinate the focused Go quality/performance evidence in #41 and denial-diagnostic volume correction in #42. If the clean public fix is breaking, use the next v0 minor line rather than silently changing v0.1.x compatibility.
3. **Initial reusable Modules + first real consumer:** use the reuse-first placement rule before a product recreates clearly shared mechanics. Identity, Admin, Media, Audit, Notifications, Search, Settings and optional Multi-Site are accepted reusable Module ownership boundaries under the [Module model](../architecture/module-model.md). Multi-Site contract/proof work is owned by #4; acceptance does not make tenancy a Core requirement or claim an implemented package. Implement only bounded real slices justified by current/near-term product needs and the owning Issues; Search waits for a real search workflow (#48), Settings waits for concrete application-level fields (#50), and Notifications waits for a real delivery flow. Keep reusable Modules in the existing AChrix repository/Go module by default and do not create empty framework surface or independent repositories/services merely because placement is shared. The first real consumer may be content/CMS, SaaS, marketplace/commerce, API/automation or another suitable product and consumes only the Modules it actually needs; its product/domain semantics remain independently owned. Use whichever suitable real consumer arrives first to prove selective capability composition, developer experience and aggregate operational cost, then generalize optional-subsystem mechanisms or tooling only when repeated real evidence earns them.
   The selected first product is [Rixa](https://github.com/AChWorks/rixa). Prepare its concrete Foundation-owned readiness slices before CMS runtime: exact optional address resolution (#4), measured operator resource configuration (#76), separately authorized clean PNG/JPEG preparation (#77) and explicit private SVG attachments (#78). Existing Core/Identity/Audit/Admin public seams cover its selected composition and fixed-grant starting needs; product ingress, permissions, content retention and actual site isolation stay product-owned. Foundation fixture evidence is not product/fleet proof, and whole #4 closure stays downstream of the real consumer/shared-update evidence. Preserve the deferred Module and owner gates above; readiness does not mean implementing every future feature.
4. **Stateful lifecycle + reusable recovery evidence:** prove simple in-product Core/Module installation/update, compatible prepared composition, migration/activation, scoped backup/restore and safe cross-component diagnosis on the first suitable real product/deployment profile that exercises this lifecycle. Routine users should need no server commands. [Issue #19](https://github.com/AChWorks/achrix/issues/19) owns the first real deployment/recovery proof; the accepted Backup & Recovery boundary is implemented through #49 only after that proof identifies genuinely reusable mechanics. Do not extract an updater or recovery daemon merely from the architectural placement.
5. **Different real consumer:** compare the accepted shared Modules against a materially different product, refine Module and Capability granularity where evidence differs and identify additional reusable capabilities without assuming every repeated feature belongs in AChrix.
6. **Additional shared assets and earned extraction:** apply the reuse-first rule to new capabilities when current evidence already makes cross-product ownership more likely than product-local ownership. Use later consumers to validate/refine those decisions. Extract independent Go modules, repositories, services or additional database/provider support only when their separate release/ownership/operations economics are actually justified.

Registry/marketplace infrastructure, every delivery adapter and speculative optional Modules are not prerequisites. Stop planning when the next bounded task is discoverable and verifiable; implement and measure to resolve remaining uncertainty.
